# Auction Draft — Architecture Map

Committed to git (unlike `SNAKE_DRAFT.md`/`YAHOO.md`/etc.) so every worktree/checkout has it automatically. Companion to [SNAKE.md](SNAKE.md) (snake/linear). Read this file before researching or changing auction-specific code; check both files' "Shared" sections for anything that touches `draftPicks`, team management, keeper rules, Sleeper/Yahoo sync, or league settings.

Format is resolved via `resolveDraftType(season, draft)` in `convex/draftType.ts`: `draft?.draftType ?? season.draftType ?? "auction"` — **auction is the default when unset**. `src/` can't import Convex runtime code, so every frontend file re-derives this inline as `(settings.draftType ?? "auction") === "auction"` (usually named `isAuction`). Auction has no feature flag — it's always available (snake/linear is gated behind `VITE_ENABLE_SNAKE_DRAFT`, see [SNAKE.md](SNAKE.md)).

## Convex schema (auction-only)

- `draftNominations` — the single "on the block" nomination + `currentBid`
- `draftBudgetPlans` / `draftLiveBudgetOverrides` — pre-draft $ allocation per roster slot + live in-draft overrides
- `drafts.nominationOrder` / `drafts.nominationOrderMode` (`"linear"|"snake"`) — a **soft, always-overridable** nomination-order suggestion. Distinct from snake/linear's authoritative `drafts.draftOrder`, even though both share the same rotation math.
- `draftPicks.price` (optional) — dollar cost; unset for snake/linear picks
- `draftPicks.planSlotKey` — which budget-plan slot ("RB2" etc.) a pick fills
- `seasons.salaryCap` / `seasonTeams.salaryCapOverride` — cap dollars (⚠ still read unconditionally by `draftValues.ts` regardless of format — see Gaps)
- `seasons.keeperRules.costMode: "dollar"` + `defaultFormula` + `tiers[].formula` — active when `costMode` is absent/`"dollar"`

- **`convex/draft/reportCard.ts`** (whole file) + **`convex/gemini/reportSummary.ts`** — grades teams on value surplus/VOR/starters-strength for both formats: auction uses real $ throughout (dollarValue surplus, keeperEstimatedValue interpolation for keepers, 50/30/20 surplus/VOR/lineup grade weights). Snake/linear runs **two deliberately different value signals for two different jobs** (settled 2026-08-30 after two rounds of user-reported bad output):
  - **Grading** (team `surplusTotal`/`surplusByPosition`, the "Surplus vs expected round" stat, and the letter grade) uses a value-implied-round comparison: `ResolvedPick.round`/`impliedRound`/`roundSurplus` = `round - impliedRound`, positive = production worth an earlier round than actually cost. `valueImpliedRound` (mirrors `src/lib/keeperCost.ts`'s function of the same name — reportCard.ts's own convex-side copy) ranks a player's own projected `dollarValue`/`keeperEstimatedValue` against the season's full VBD value curve (`values` from `getRealDraftValues`, sorted descending). `teamValueOf` routes surplusTotal/percentile grading through this. Grade weights are format-specific (`AUCTION_GRADE_WEIGHTS` 50/30/20 surplus/VOR/lineup vs. `SNAKE_GRADE_WEIGHTS` 25/50/25 — snake weights VOR higher since round-based surplus is a noisier signal, user-requested 2026-08-30).
  - **Individual-pick callouts** (`leagueSteals`/`leagueReaches`, each team's `bestPick`/`worstPick`/`bestKeeper`/`worstKeeper`, and the expanded per-pick table's display) use real market ADP: `ResolvedPick.adp`/`adpSurplus` = `slot - adp`, blended from Sleeper `adpForScoring` averaged with ESPN's overall rank (ESPN-only for superflex — reportCard.ts's own copy of the same blend `src/lib/valueRank.ts`/`preDraftInsights.ts` use, scoped to `CALLOUT_POSITIONS`/QB-RB-WR-TE).
  - **Why two metrics, not one**: v1 (pure ADP vs. slot, 2026-08-29 AM) mis-graded late-round picks because deep-bench ADP is noisy (many leagues never draft that deep, so it reads almost every deep pick as a reach). v2 (pure value-implied-round, 2026-08-30 AM) fixed grading but then read *every* 16th/17th-round pick as if it were an 8th/9th-round "steal" instead — the opposite bias, for the opposite reason: the value curve's own $1-floor tie-clustering (see `valueImpliedRound`'s comment) systematically over-credits every deep bench player. v3 (2026-08-30 PM) added consensus gating: `calloutValueOf`/`calloutKeeperValueOf` only treat a pick as a steal/reach when `adpSurplus` AND `roundSurplus` agree on sign (`Math.sign` match); on disagreement the pick is excluded from steals/reaches/best-worst-pick/best-worst-keeper entirely, same null-handling as "no real ADP." **v4 (2026-08-30 PM, current)**: grading alone was *still* reading every team's total as deeply negative (a -200 best-team total). Root cause: `values` (`getRealDraftValues`) pools hundreds of ranked players per position — Sleeper's pools go far deeper than any real roster — so once VOR hits 0, the tied group at the $1 floor is often several hundred players wide. Even averaged (v2's fix), a tie group that size implies a round deep into the 20s-30s for a 12-team league, which every real replacement-level pick (drafted in the actual, much shallower 12-18 round range) then reads as a huge reach - not a real skill signal, just the pool being far deeper than any draft goes. Confirmed switching the ranking input from `dollarValue` to raw VOR would NOT help AT THE TIME (verified in code: with VOR *also* floored at 0 back then, `dollarValue = 1 + (VOR^FALLOFF_EXPONENT / totalWeight) * surplusDollars` was a strictly monotonic transform of VOR — identical order, identical ties, identical oversized floor group). Fix (still current): exclude VOR<=0 picks from `roundSurplus` entirely (`impliedRound` stays `null`, contributing 0/neutral to `surplusTotal`) rather than ranking them at all - there's genuinely no ROUND-implying signal worth grading on below replacement level, a judgment call independent of whether VOR itself is floored (see `src/lib/valueRank.ts`'s entry below - VOR stopped being floored a few hours later for a *different* consumer, "our rank," but this grading exclusion was deliberately left as-is). The ADP number is still what's displayed for callouts - the value curve is purely a same-direction veto. A league can legitimately end up with fewer than 5 leagueSteals/leagueReaches, or a smaller `surplusTotal` magnitude than before, if it has many VOR<=0 picks (deep benches, K/DST) - expected, not a bug.
  
  Both signals need no separate keeper interpolation the way auction's `keeperEstimatedValue`/`keeperSurplus` split does: `valueImpliedRound`/ADP each already take `keeperEstimatedValue` as an input the same way they take a real pick's `dollarValue`/market read. K/DST are excluded from callouts (`CALLOUT_POSITIONS`) but not from grading — their value is too thin/clustered, so either metric reads a slight edge as a false "steal" a real draft wouldn't treat as one. `efficiencyDollarsPerVor` is auction-only (null for snake/linear). The frontend (`DraftReportCard.tsx`) and Gemini prompt (`reportSummary.ts`) both read `data.isAuction` and never render/mention `$`/dollars for a snake/linear league, and never blend the two rounds/ADP units in one sentence. `draftReportCardSnapshots` rows carry a `version: REPORT_CARD_VERSION` marker so a snapshot frozen under an older shape/logic self-heals (recomputes in place) instead of serving stale/incompatible content — bump it whenever `ResolvedPick`/`ReportCardData`'s shape *or* grading logic changes again.

- `convex/draftValues.ts`, `convex/valueGaps.ts` — VBD/points/ADP-gap caches computed for every format (⚠ `dollarValue` specifically is auction-flavored but computed unconditionally — see Gaps). `valueOverReplacement` is genuinely unclamped (can go negative for a below-replacement player) as of 2026-08-30 - only the `weight`/`dollarValue` formula floors its own input at 0 (`Math.pow` of a negative base to `FALLOFF_EXPONENT` - a fractional exponent - is `NaN`, so that floor has to happen somewhere regardless); `dollarValue` itself is unaffected, still floors at exactly $1 for any at-or-below-replacement player.   - **Default sort is "Rank" everywhere now (2026-08-30, user request)**: `PlayersTable.tsx`'s `sortedRows` and `PlayersLeftTab.tsx`'s `tableRows` both used to default to `"dollar"` ($/ADP) until a header was clicked; `SnakeDraftTab.tsx`/`MobileSnakeDraft.tsx` already defaulted to `"rank"` from when their own Rank columns were added. `PlayersTable.tsx`'s desktop-only "Rank" column (`renderSortableTh("Rank", "rank")`, first column) predates this session and is universal (not format-gated) - it displays the row's position in the current sort (`index + 1` in `PlayerRow.tsx`), not a separately-fetched fpid-keyed number, so it only reads as a real absolute rank once the table is actually sorted by Rank - which defaulting to it fixes. `PlayersLeftTab.tsx` has no such default-agnostic Rank column for auction (its Rank column is snake/linear-only, added the same day - see the Shared Frontend entry below), so its default stays format-aware: `"dollar"` for auction (no separate Rank concept there - $ already is one), `"rank"` for snake/linear.
  - **`buildOurRankByFpid`'s ranking key (iterated twice, 2026-08-30):** it used to rank by `dollarValue` (`rankByDollarValue`), which floors at exactly $1 for every at-or-below-replacement player - a huge tied block (once VOR hits 0, everyone shares that floor). First fix averaged (and rounded) each tied group's rank instead of handing out ranks by array-iteration order (a real bug: a QB with 0 projected points read as the league's overall rank 79 purely because QB rows were assembled before RB/WR/TE - see `convex/draftValues.ts`'s comment). That was correct but still produced a large single tied block (e.g. "rank 157" repeated for 150+ players) - fair, but not useful UX. Real fix: `convex/draftValues.ts`'s `valueOverReplacement` stopped being floored at 0 (only the `weight`/`dollarValue` formula still floors its own input, for the `Math.pow`-of-a-negative-fractional-exponent reason noted in the Shared section above), and `buildOurRankByFpid` now ranks by `signedCurveValue(valueOverReplacement)` - the SAME `VOR^FALLOFF_EXPONENT` curve `dollarValue` uses above replacement, extended symmetrically below zero (`Math.sign(vor) * Math.abs(vor) ** FALLOFF_EXPONENT`) rather than raw VOR directly (raw VOR isn't cross-position comparable - a below-replacement QB's raw point deficit is a different scale than a TE's - which is exactly why the curve exists at all; extending it keeps that normalization in both directions). Ties are now rare (only genuine point ties) rather than the norm below replacement. `rankByDollarValue`'s original tie-averaging logic was generalized into a shared `assignAveragedRanks` helper, still used by both it (dollarValue, unchanged, still the keeper-bargain ranking key elsewhere - `keeperCost.ts`/`RecommendedKeepers.tsx` are untouched) and the new curve-based ranking.
  - Displayed rank numbers are plain (`23`, not `#23`) everywhere.
  - Tier column is unchanged either way (already format-agnostic). The two tables differ on how they surface the rank number: `PlayerRow.tsx`/`PlayerRowMobile.tsx` (pre-draft PlayersTable, no separate Rank column) still use `AdpValueLabel.tsx`, whose rank number is real always-visible text, not a hover `Tooltip` - a Tooltip is unreachable with no hover state on a touch device, which made "what does our own math rank this guy" invisible mid-draft on mobile (user report, 2026-08-30); `PlayerTableRow.tsx`/`PlayerTableRowMobile.tsx` (in-draft PlayersLeftTab) instead give Rank its own standalone sortable column, positioned first before Player (a follow-up user request, same day, after `AdpValueLabel`'s combined rank+diff cell was judged not enough on its own for `SnakeDraftTab.tsx`/`MobileSnakeDraft.tsx` - see SNAKE.md's entries), with vs-ADP as a separate plain-text diff column computed inline (`adpDiff`) instead of reusing `AdpValueLabel`. `StandardValueLabel.tsx` (auction's counterpart) still gates its own rank behind a Tooltip, untouched, since desktop hover works fine there and the report was snake/linear-specific.

- **`src/lib/slotAssignment.ts`'s `optimalAssignPicksToSlots`** — format-agnostic, points-only lineup optimizer (sorts each team's picks descending by `pointsByFpid`, fills fixed slots first, pools leftovers into FLEX/SUPERFLEX/bench) called by `MyTeamTab.tsx`, `LeagueTab.tsx`, `SeasonSummary.tsx`, and `DraftBoard.tsx`. It silently treats any pick missing from its caller-supplied `pointsByFpid` map as 0 points (`pointsByFpid.get(pick.fpid) ?? 0`) — **do not build that map from `draftValues.ts`'s `values`/`getDraftValues(Public)`**, since `computeDraftValuesForSettings` deliberately filters `keptFpids` out of its pool before pricing (they're off the board before an auction even starts), so every keeper's fpid is simply absent and reads as 0 points, pushing every keeper to the bottom of the bench regardless of real projection (user report, 2026-08-30, present in all four call sites at once — auction and snake/linear alike, since keepers exist in both formats and this optimizer is shared). Fixed by building `pointsByFpid` from `allProjections` (raw `projections` rows, includes keepers) via `pointsForScoringConfig`/`scoringConfigFromSeason` (`src/lib/relevantPlayers.ts`) instead — the same computation `draftValues.ts` uses internally, just not gated on "was this player ever auctionable." `convex/draft/reportCard.ts`'s own backend lineup optimizer already did this correctly (its keeper-fallback branch always looked up `projections` directly) and never had the bug. `DraftBoard.tsx`'s fix also dropped its `getDraftValuesPublic` query entirely, since points were its only remaining use of the $ engine there (see that file's own top-of-file comment about deliberately never reading `dollarValue`).

**Critical invariant**: `costMode` (written by `KeeperRulesPanel.handleSave` as `isSnakeOrLinear ? "round" : "dollar"`) is the schema source of truth for $-vs-round keeper formula, but every frontend reader (`KeeperSearchForm`, `RecommendedKeepers`, `SleeperKeeperSuggestions`, `KeeperCardList`, `KeeperPriceCell`) independently re-derives `isSnakeOrLinear` from `settings.draftType` rather than reading `costMode`. **These two must never drift** — nothing enforces agreement if `draftType` and `keeperRules.costMode` are ever changed independently.

## Known gaps / landmines

1. `nominate`/`bumpNominationBid`/`setNominationBid`/`passNomination`/`undoNomination`/`resolvePick` have **no `resolveDraftType` check** — nothing server-side stops calling them against a snake/linear season. Only the frontend not calling them protects this boundary (contrast with `draftPick`, which explicitly throws for auction).
2. `setKeeperPrice` patches `price` unconditionally, with no check the season is actually auction-typed.
3. `setTeamSalaryCap` has no format guard; `dollarValue`/`totalCapDollars` are computed unconditionally in `draftValues.ts` regardless of format.
4. ~~Report Card ran unconditionally for snake/linear with meaningless $ grades~~ — **resolved 2026-08-29**: `reportCard.ts` now computes an ADP-vs-slot analog for snake/linear (see the Shared section above), so `syncDraftStatus`'s unconditional scheduling is now correct for every format.
5. Live Sleeper sync's snake/linear round math (`convex/sleeper/draftSync.ts`) trusts the app's own `drafts.draftOrder`/`reversalRounds` config, not Sleeper's raw slot numbers — if the host's in-app Draft Order doesn't actually match the real Sleeper draft's order, synced picks will land in the wrong `pickInRound`/`overallPick` slot on the board (the pick's `teamId` itself is still always correct). Not yet tested against a real live snake/linear draft.
